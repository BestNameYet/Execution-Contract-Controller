# Simplified Transaction Layer Requirements

This table is the implementation checklist for the isolated simplified transaction layer under `minimal-controller-design/simplified-transaction-layer/`.

`MET` means the requirement is implemented by executable code in this subfolder and the exact script/line evidence is listed. `SPECIFIED` means the requirement is authoritative for this layer but implementation evidence has not yet been verified. `UNMET` means verified executable behavior is required and absent.

| ID | Requirement | Status | Scripts / lines where requirement is met |
|---|---|---|---|
| STL-001 | The simplified transaction layer must remain isolated from the existing `minimal_controller.py`; implementation in this folder must not modify the existing controller unless explicitly requested. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-002 | The transaction layer must accept executable script source as its transaction input. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-003 | For a transaction containing a script, the transaction layer must create/use one runner and execute exactly the supplied script source in a child process. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-004 | The runner must use a single `subprocess.Popen(...)` child for the supplied script so the script can remain alive across multiple I/O exchanges. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-005 | The transaction boundary must transparently carry caller/model input downward to the running script's stdin without interpreting its semantic content. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-006 | The transaction boundary must transparently carry the running script's stdout upward to the caller/model without interpreting its semantic content. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-007 | The transaction boundary must transparently carry the running script's stderr upward to the caller without interpreting its semantic content. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-008 | A running script must be able to perform multiple stdin/stdout exchanges during one child-process lifetime before the script terminates. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-009 | The transaction layer must remain semantically content-neutral: it must not interpret the meaning of stdin, stdout, stderr, or arbitrary script contents. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-010 | The transaction layer must record every observable stdin use at the transaction boundary, preserving the data transferred downward and its order relative to other recorded transaction events. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-011 | The transaction layer must record every observable stdout use at the transaction boundary, preserving the data transferred upward and its order relative to other recorded transaction events. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-012 | The transaction layer must record every observable stderr use at the transaction boundary, preserving the data transferred upward and its order relative to other recorded transaction events. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-013 | While the child is running, all transaction event records, including stdin/stdout/stderr observations and transaction-state observations, must be accumulated in local memory; the transaction must not incrementally persist the receipt during execution. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-014 | The normal transaction unit is finite: the transaction remains active while its supplied script is running, and normal receipt finalization begins after that script terminates and its child process closes. Persistent systems must expose finite operations as separate transactions when completed receipts are required. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-015 | A transaction invocation with no script must execute no child script but must still generate and persist a transaction receipt describing the no-script transaction. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-016 | The transaction layer must not infer whether arbitrary unlabeled text is executable by inspecting its contents; execution occurs only through the explicit script-oriented transaction path. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-017 | The implementation must preserve subprocess isolation: supplied script execution occurs in the spawned child rather than directly in the transaction process. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-018 | Stream recording and receipt generation must not alter, rewrite, or semantically consume the stdin/stdout/stderr data being transferred between caller and child. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-019 | The transaction must record its transaction states sufficiently to reconstruct the transaction lifecycle and the key environmental conditions observable at the transaction boundary. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-020 | The receipt must record the exact function used to initialize/create the child runner and the concrete initialization/invocation information needed to identify how the child was created. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-021 | The receipt must preserve the exact script source supplied for the transaction, not merely a digest or derived representation of the script. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-022 | The finalized receipt must contain the transaction identity, transaction start/close timing, recorded transaction states, child-initialization provenance, exact supplied script, complete ordered stdin/stdout/stderr event transcript, receipt destination, and persistence/integrity metadata. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-023 | Receipt persistence must occur once, after the child has closed and the complete in-memory transaction record has been frozen; transaction event activity must not cause incremental receipt-file writes. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-024 | The transaction must support persisting the receipt to a caller-specified local filename or, when no filename is supplied, to a transaction-specific generated local receipt file. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-025 | During receipt persistence, the transaction must write the frozen in-memory receipt to the selected local receipt file and then verify that a receipt exists at that destination. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-026 | After writing the receipt, the transaction must read the persisted receipt back and deterministically verify that the persisted receipt matches the frozen in-memory receipt object that was used for the write. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-027 | Receipt persistence is not successful unless the post-write existence/read-back/equality verification succeeds; a missing, unreadable, malformed, or mismatched persisted receipt must be treated as receipt-persistence failure. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-028 | The receipt must include integrity metadata derived deterministically from the receipt contents so persisted receipt integrity can be checked without semantic interpretation of transaction content. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-029 | The transaction layer itself must not perform JSON-validity gating, semantic result derivation, `script`-field continuation, next-script selection, or other higher-level DTM/execution-control progression; those behaviors belong outside this neutral transaction layer. | SPECIFIED | Implementation evidence not yet verified against this revised table. |
| STL-030 | Child termination is used as the finite transaction boundary for receipt finalization; the transaction layer need not interpret a process exit code as a semantic transaction result. | SPECIFIED | Implementation evidence not yet verified against this revised table. |

## Current verification state

This requirements revision defines the current transaction-layer contract. It intentionally removes the earlier JSON-validation/continuation requirements and the requirement to derive a semantic transaction result or treat a final exit code as such. Code compliance has not yet been evaluated against this revised requirements table; that is a separate next step.
